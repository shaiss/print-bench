# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Purpose

This repository holds 3D-printable designs co-designed in OpenSCAD. Each design is a parametric `.scad` file; the deliverables are STL files ready for slicing, plus PNG previews so the design can be reviewed without a 3D viewer.

## Environment

OpenSCAD (2021.01) runs headless here — there is no display, so every invocation must go through `xvfb-run -a`. Rendering with plain `openscad` will fail.

The scripts honor `OPENSCAD_BIN` (default `openscad`) and `OPENSCAD_ARGS`: CI's render gate runs the dev snapshot with `OPENSCAD_BIN=openscad-nightly OPENSCAD_ARGS=--backend=manifold` (order-of-magnitude faster full renders), while the stable 2021.01 check job keeps designs compatible with the release build. Locally the default is whatever `openscad` is installed; don't use nightly-only flags (like `--backend`) in scripts or designs without going through `OPENSCAD_ARGS`.

The SessionStart hook (`.claude/hooks/session-start.sh`) installs the toolchain a session actually needs: openscad, xvfb, imagemagick, prusa-slicer, printcheck and stylelift (with pytest). If any of them is missing mid-session, run `.claude/hooks/session-start.sh --force` rather than working around the gap (`--force` is needed outside Claude Code on the web, where the hook otherwise no-ops) — `gate.sh --slice` must be runnable locally.

`bpy` (Blender as a Python module, behind `product-shot.sh`) is **not** installed by default: CI renders and commits the product shots now, so a session doesn't need a ~1 GB wheel to ship a design. Run `.claude/hooks/session-start.sh --force --with-bpy` if you want to preview a shot locally — both flags, because without `--force` the hook no-ops outside Claude Code on the web. `bpy` is a module rather than a command, so `command -v` won't find it; check with `python3 -c 'import bpy'`.

## What CI generates, and what you write

Anything **derived** from a design is CI's job, not yours. The `regen` job in `.github/workflows/ci.yml` re-runs `render.sh --previews`, `animate.sh`, `product-shot.sh` and `gallery.sh` for every design a PR touches (blast radius included), drafts a product page with `product-page.sh` when one doesn't pass its gate, and commits the result back to the PR branch. It skips a design whose input fingerprint (`scripts/regen-stamp.sh`) still matches the committed `designs/<name>/previews/.regen-stamp` — re-rendering a Cycles shot to discover it is byte-identical costs minutes — and refreshes the stamp in the same commit as the artifacts, so a stamp can never claim freshness the artifacts don't have. Don't run those generators to produce something to commit — run them when you want to *look* at the output.

That holds wherever CI can push, which is every branch in this repository. **On a PR from a fork it does not**: `regen` cannot write to a fork, so it fails with the list of files instead, and there you do run the generators and commit their output yourself. Everything below describes the normal case.

That is not only a convenience. Every gate on these artifacts is presence-only, precisely because a human used to commit them: `readme-gate.sh` checks a preview exists, is embedded and is under budget, never that it depicts current geometry. Issue #69 is that hole — three `desiccant-capsule` previews still showed a thread profile the design no longer had, and CI passed them clean. Regenerating in the same run that gates the source closes it: a committed image cannot be older than the source beside it.

Three consequences worth knowing.

The commit-back is pushed with the **`REGEN_TOKEN`** secret (a fine-grained PAT with `contents: write`), not `GITHUB_TOKEN`. A `GITHUB_TOKEN` push triggers no workflow, and check runs attach to the commit a run started on — so committing back with it would move the PR head onto a commit carrying none of the required contexts, with nothing left to add them, and the PR could never merge. The PAT push does trigger a run, so the checks land on the commit that actually ships. Without the secret `regen` still regenerates and commits, but fails the job with an explanation rather than stranding the PR silently.

That re-trigger means a regenerating PR runs CI twice. The second run is the verification pass, and a **loop guard** bounds it there: `regen` recognises its own commit at `HEAD` and refuses to push a second time. Without that, a generator that isn't byte-stable across runners — Cycles picks its CPU kernel by instruction set — would push, re-trigger, and push again forever. If the second pass does produce different bytes, it warns that the generator is non-reproducible instead of chasing it.

And CI cannot push to a fork, so a PR from a fork fails the `regen` job with the list of files to regenerate by hand instead of silently skipping them.

Set `OPENSCADPATH="$PWD/lib:$PWD"` (the scripts do this automatically): `lib/` resolves library includes, and the repo root resolves `include <styles/<name>/style.scad>`. Available libraries:

- **BOSL2** (vendored at `lib/BOSL2/`, **BSD-2-Clause**) — `include <BOSL2/std.scad>`. Use for fillets/roundings (`cuboid`, `cyl`), attachments, threads (`include <BOSL2/screws.scad>`), gears, and anything geometrically hard. Prefer it over hand-rolled hulls for rounded/filleted parts.
- **NopSCADlib** (vendored at `lib/NopSCADlib/`, **GPL-3.0**) — `include <NopSCADlib/core.scad>`. Hardware catalogue and assembly tooling: vitamins (screws, nuts, washers, bearings, PCBs, extrusions …), printed parts, and the BOM/exploded-view primitives the assembly-docs feature (#98) is built on. The **GPL-3.0 boundary is materially different** from BOSL2's BSD-2-Clause: a design that `include`s NopSCADlib and exports geometry is a GPL-3.0 combined work, and must **disclose on its product page** that it incorporates a GPL-3.0-licensed part; the repo's derivative/lineage system keeps such a design an isolated, attributed unit so the obligation does not spread to designs that do not use NopSCADlib (see `LICENSE`, the vendored-code paragraph, and `lib/NopSCADlib/VENDORED.md`). GPL/copyleft must **not** reach shared first-party core — `scripts/`, the site, `lib/*.scad` — a **standing decision** (issue #160; full policy in `docs/licensing.md`) enforced by `scripts/license-boundary-check.sh`, not a deferral: a design may opt in, shared core code may not, and core may invoke GPL tools it does not ship (openscad, prusa-slicer, bpy) but may not bundle vendored copyleft source. Vendored as mere aggregation like BOSL2: never edit `lib/NopSCADlib/`. `scripts/nopscadlib-check.sh` proves the include resolves through `OPENSCADPATH` (run by `check.sh`), so the vendored tree cannot silently go missing the way an unresolved `include` only WARNs.
- **MCAD** (system-installed) — `include <MCAD/...>`.
- **`lib/printability.scad`** — repo-local FDM helpers: `screw_hole()` (plain/socket/countersunk, M2–M6 presets), `teardrop_hole()` (support-free horizontal holes), `heatset_boss()`, `chamfered_cylinder()`, `rounded_box()`. Lightweight and fast; reach for these before BOSL2 for simple fastener work.
- **`lib/threads-fdm.scad`** — printable trapezoidal threads for vertical bores: `thread_helix()` (the generator), `thread_neck()` (male, with lead-in chamfer), `thread_bore_cut()` (the matching female cutter), `flank_add()` (the clearance derivation). 45° flanks so both halves print supportless, one tunable radial `tol`, and both profiles from one generator so male and female cannot drift apart. The clip masks derive their oversize from what they must clear and never tessellate coarser than `seg`, so a caller's coarse `$fn` cannot shave the crest and a large `tol` cannot be silently capped (issue #64). Use it over BOSL2's `screws.scad` for printed threads; use BOSL2 for machine threads.
- **`lib/print-in-place.scad`** — print-in-place sliding mechanisms, extracted verbatim from the archived `sushi-battleship` at v0.1 (issue #19; the frozen design keeps its inline copies, and the extraction is parity-proven against its renders — evidence in the lib header): `slide_rail()` (castellated locking lips for one bay side), `slide_tab()` (the matching door tabs), `end_stop()` (travel-bounding ridge, weld-gap guarded), `sacrificial_membrane()` (the window cutter whose raised start *is* the membrane), `pip_hinge()`/`pip_hinge_pin()` (teardrop-bore hinge on `printability.scad`'s profile, the bore grown from the pin's own 2D profile by a true `offset(r=clear)` — a scaled teardrop leaves the 45° flank planes coincident, a welded print only the Manifold render exposed), plus the clearance derivations (`pip_lip_z()`, `pip_rail_h()`, `pip_tab_centres()`, `pip_lip_profile()`). The clearances carry the battleship's **acoustic property** — tuned to slide without rattling, because a loaded cell that sounds different from an empty one is a wallhack in a hidden-information game — so tune the door-side `fit` on a coupon, never the rail clearances upward. Use it for print-in-place doors, shutters and hinges; use BOSL2 for generic joints.
- **`lib/nuggs-coupling.scad`** — the NUGGS genderless quarter-turn bayonet port, the one interlock standard every NUGGS module shares: `nuggs_cfg()` (the config vector every guard fires inside), `nuggs_port()` (one port face — **not bore-clean**, see below), `nuggs_bore_cut()` (the cut every caller of `nuggs_port()` owes), `nuggs_neck()` (port + full-round shell + the cut, as one bore-clean solid — prefer it), `nuggs_window()` (the longitudinal window that turns a neck-and-tube into an open module), `nuggs_sector()` (the one-swept-polygon primitive), plus the caller's contract values (`nuggs_ri/ro/r_mid/r_out/pitch/z_tip/z_seat/z_top/clockings/tol_deg/rib_in/i_out/bearing_area/web/walk_half_deg`). Two things it does that no other library here does, both deliberate: it **pins its own `$fa`/`$fs`** inside every module body and ignores the caller's, because the fit is split at one radius and every surface is a `rotate_extrude`, so an unpinned clearance moved with the caller's quality preset (measured on the pre-extraction geometry, the insertion clocking left 0.1754 mm³ of interference at `$fn=48`, 0.0717 at 56, 0.0260 at 64 and came out free only from 96 up — and `mate-check.sh` renders at exactly 96, so the harness could never have seen it); and it emits material **inside the bore** on purpose, so a caller that forgets `nuggs_bore_cut()` ships a watertight, sliceable, 100/100-scoring part with plastic standing in the bore. Use it for anything that has to mate with a NUGGS module; it does one joint, so reach for BOSL2 for threads, gears or generic rounding.
- **`lib/printer-conf.scad`** — the print-feedback profile (issue #101): the printer characteristics a design reads to pre-fill its tuned-fit parameters instead of hardcoding a generic clearance. Defines generic defaults (`printer_xy_tol`, `printer_nozzle_d`, `printer_material`) and a `printer_fit(nominal)` helper, then `include <printer.conf>` (the repo-root profile, committed inert) to let measured values override them — last-assignment-wins, exactly how a style pack's tokens are `include`d. A design opts in with `include <printer-conf.scad>`; nothing else includes it, so it adds no dependency to designs that don't. `printer.conf` is committed as an inert stub precisely so the include always resolves (a missing include is a fatal wrong-geometry warning in `check.sh`, not a no-op); leaving it inert is the feature's off state. `scripts/printer-conf-check.sh` proves the default/override resolution reaches the exported mesh. See `docs/print-feedback.md`.
- Each **first-party** library (the `lib/*.scad` files above; not vendored BOSL2 or system-installed MCAD) ships a `lib/<name>-demo.scad` exercising every module; `check.sh` CGAL-renders all of them, so they are those libraries' regression tests. Add one with any new first-party library. A library whose modules carry guards also ships `lib/<name>-guards.conf` — one line per parameter set the library must **refuse**, run by `scripts/guard-check.sh`. That is the half a demo cannot cover: a firing assert aborts the render it lives in, so without those cases a guard can be weakened or deleted and every check in the repo stays green. A library with a **tuned fit** (a mating pair, a clearance) also ships `lib/<name>-mates.conf` — one line per pair that must **assemble**, plus at least one deliberately-interfering case proving the check can fail, run by `scripts/mate-check.sh`. That is the other half a demo cannot cover: a render cannot measure itself, so a demo can only restate the clearance formula, which proves the formula equals itself while the built geometry drifts (issue #37).

## Smart CI (gate selection)

CI has two layers of gate selection. The **deterministic** one is the `changes`
job in `.github/workflows/ci.yml`: it reads a PR's changed files and picks which
of the gates that **already exist** run (design-only PRs gate just the designs
they touch, docs-only PRs skip the render jobs, and so on — see the CAUTION and
tier notes at the top of that file). That decision lives in one extracted
script, `scripts/ci-classify.sh`, that the `changes` job pipes its diff to and
`/preflight` runs `--local` — so the "would CI pass?" check on the working tree
can never drift from what the workflow actually does. The **smart** one is
`tools/ci-gates/`, the layer on top: it proposes gates that *don't exist yet*.

The mechanism is three parts kept separate on purpose:

- **detectors** (`tools/ci-gates/src/ci_gates/detectors.py`) decide whether a
  candidate gate *applies* to a PR — pure functions of the changed-file list and
  the tree. Seeded: `classifier-coverage` (a changed file under a top-level dir
  the `changes` classifier doesn't mention — the CAUTION footgun as a check),
  `shellcheck` (a `*.sh` changed), `actionlint` (a workflow changed).
- **registry** (`.github/ci-gates/registry.conf`) records the *decision* about
  each candidate — `on` / `proposed` / `off` — and its **tier**. It is the
  reproducible source of truth: it lives in git, a clone carries it, every run
  reads it identically. GitHub supplies only the interaction and the auth.
- **selector** (`ci_gates select`) joins the two into buckets the `smart-ci`
  job runs and the sticky PR comment reports.

The **auto-approve policy** is the tier: an **advisory** gate (cheap,
non-blocking) is `on` by default and runs whenever it applies with no human
step; a **gating** gate (can fail a PR) defaults to `proposed` and stays a
proposal — surfaced in the comment — until a human crosses it, so a new blocking
check never lands unannounced. A gate is known to selection only if it has a
stanza in the registry; within that stanza the `state` field is what may be
omitted, and it falls back to the tier default — so a gate's decision can be
left implicit, but the gate (tier, title, run) must be declared.

Crossing a proposal is GitHub-native: a maintainer posts a PR comment with the
command (note the leading slash):

```text
/ci-gate approve <id>      # wire the gate in for this and every future run
/ci-gate decline <id>      # turn it off so it stops being proposed
/ci-gate list              # show the current selection
```

The `ci-gate-approve.yml` workflow authorizes them by their real repository
permission, flips the gate's `state` in the registry, and commits that one-line
change to the PR branch **via the Contents API** with `REGEN_TOKEN` (same secret
and reason as `regen` — a PAT-authored commit re-triggers CI so `smart-ci` runs
the newly-enabled gate; a `GITHUB_TOKEN` commit would not). That workflow is
privileged (`issue_comment` holds the secret), so it never checks out or runs
the PR head's code — it edits the head branch's `registry.conf` as data with the
base repo's trusted tooling. Future runs then enforce the gate by construction,
because the registry said so. From a fork (uncommittable), the comment says to
edit `registry.conf` in the PR instead.

`smart-ci` runs on every PR and every push with no early skip (a skippable job
can't satisfy branch protection — the same PR #50 reason `ci-ok` documents), and
is one of `ci-ok`'s `needs`. By default it only runs the advisory
`classifier-coverage` detector, so it cannot start failing PRs on its own until
someone crosses a gating gate. `tools/ci-gates` has its own pytest suite (the
`smart-ci selector unit tests` job); a malformed registry stanza fails it.

## The AI andon cord

One repo variable, **`AI_ANDON_CORD`**, set to the word `pulled` (GitHub's
case-insensitive compare, so `Pulled` too; unset or anything else = released)
bypasses **every AI-consuming workflow job** at once — the twelve scheduled
agent routines, the groomer's narrative step, the Jane/Drik/PM-triage/coach
reviewers and the Oracle, CI's product-page drafting step, the three Z.AI image
generators and the model smoke — grey/skipped, never red, no provider API call,
no `needs-decision` escalation, exactly one `::notice::` per bypassed run.
Every deterministic job keeps running unchanged: the CI gates, `regen`'s
previews and gallery, Reeve's report and observer, the groomer's report,
telemetry, the decide command. It is a control, not policy (N4): it overrides an
armed routine without touching its arming variable or conf. The hourly
`andon.yml` reconciler (`tools/andon`) opens one `andon-cord`-labeled status
issue on the first observed pull and closes it with the timespan on release;
Reeve's report carries a 🛑 banner line while pulled. Collateral: the
fail-closed `reviewer-signoff` status BLOCKs a design PR lacking two clean
current sign-offs until release (or `signoff-override`). Enforced by the
model-registry drift guard (every job touching a provider secret, the
claude-code-action or provider-triage must carry the gate leg), `tools/andon`'s
suite, `reviewer-signoff.sh --selftest` and Reeve's golden pair. Design of
record: `docs/andon-cord.md`.

## Commands

All commands run from the repo root.

```bash
# Render STL + 4-view preview PNG for one design (or all designs with no args)
./scripts/render.sh <name>

# Fast syntax/eval check of every .scad in the repo + lib geometry regression
# test + lib guard negative tests (scripts/guard-check.sh: every guard still
# refuses what it exists to refuse) + lib mate positive tests
# (scripts/mate-check.sh: every declared fit still assembles, measured as zero
# facets of interference) + docs-drift check (scripts/docs-check.sh: docs must
# match the tree)
./scripts/check.sh

# Report-only sca2d static analysis of first-party .scad files (pip install sca2d)
./scripts/lint-scad.sh

# Render printable parts (designs/<name>/ci.parts, if present) and gate the
# STLs with tools/printcheck; --slice adds a PrusaSlicer test-slice. A
# designs/<name>/ci.fitchecks manifest additionally gates boolean fit parts:
# `<part> empty` must render zero facets, `<part> interferes` is the mandatory
# negative control proving the check can fail. A designs/<name>/ci.fusecheck
# manifest additionally runs the deterministic fuse detector (tools/printcheck's
# `fusecheck`) on the SLICED STL — never a -D pose — to catch a print-in-place
# mechanism that welds shut (a living hinge stays watertight and one body, so
# printcheck can't see it): `flexure <aabb>` drops the thin hinge zone,
# `assert <stl> <min>` requires the rest to split into >= min separable bodies
# (a fuse is a STRONG WARN needing reviewer signoff, not a hard fail), and
# `control <part> <max>` is the mandatory known-fused negative control proving
# the check can still fire. CI runs this.
./scripts/gate.sh [--slice] [<name>...]

# Lineage of derivative designs (designs/<name>/derives.conf): `check`
# validates every record and is run by check.sh; `blast-radius` answers what
# a change to a design has to re-gate, which is how CI scopes the gate.
./scripts/lineage.sh check [<name>...]
./scripts/lineage.sh blast-radius <name>...
./scripts/lineage.sh parents|children|ancestors|descendants <name>
./scripts/lineage.sh graph [--format text|json]   # `order` for gallery order

# Re-prove the derivative gate can still fire: renders fixtures carrying a
# working override and a typo'd one and asserts the mesh comparison still
# tells them apart. Run it after any OpenSCAD upgrade.
./scripts/lineage.sh selftest

# Check every design ships a product-page README.md (title, intro pitch,
# preview image, Print settings + Parameters sections). CI runs this.
./scripts/readme-gate.sh [<name>]

# Render animated GIF previews (designs/<name>/animations.conf, if present)
# into designs/<name>/previews/. CI regenerates and commits these; run it
# locally only to look at the result before pushing.
./scripts/animate.sh [<name>]

# Render real-world-looking product shots (designs/<name>/shots.conf, if
# present) into designs/<name>/previews/: OpenSCAD exports the STL, Blender's
# Cycles path-traces it in a studio scene (soft lighting, glossy floor, FDM
# layer lines). CI regenerates and commits these; running it locally needs bpy
# (session-start.sh --with-bpy). See /product-shots.
./scripts/product-shot.sh [<name>]

# Draft a design's product page (README.md) with the Claude API from its .scad
# parameters, NOTES.md and preview manifests. Only acts when readme-gate.sh
# already rejects the page, and reverts its own draft if the gate rejects that
# too — the gate decides what is acceptable, never the model. Needs
# ANTHROPIC_API_KEY (a repo secret); CI runs it in the regen job. The result is
# a DRAFT for a human: it carries a marker comment to delete after review.
ANTHROPIC_API_KEY=... ./scripts/product-page.sh <name>   # or: --mock, --force

# Generate an AI-restyled shot via the Z.AI GLM-Image API in image-to-image
# mode — seeded from a committed geometry-true render (previews/<ref>.png via
# seed=<ref>). On this provider the seed does NOT constrain the geometry to the
# real mesh (issue #302), so the result is AI and geometry-approximate; the
# disclosure, not any fidelity guarantee, is what keeps it honest, and the
# tier-1 render and STL remain the source of truth for the real shape. --kind
# selects the manifest and tier (same script, no new file):
#   --kind lifestyle (default): reads designs/<name>/lifestyle.conf, writes a
#     tier-2 *lifestyle* scene (previews/lifestyle-<shot>.png — a world around
#     the part; seed may be a tier-1 render or a tier-1.5 product still).
#   --kind product-still: reads designs/<name>/product-still.conf, writes a
#     tier-1.5 *product still* (previews/product-still-<still>.png — the BARE
#     part in isolation, photoreal, shown on the page; its angle is whichever
#     tier-1 shot seeds it, since an image-to-image still has no camera of its own).
# Both size to budget and embed with the disclosure readme-gate requires. Needs
# ZAI_KEY (a repo secret). CI runs each via its workflow — "Lifestyle shot
# (tier-2, AI)" and "AI product still" — automatically when the matching manifest
# lands on main, or on demand — each opening a draft PR to approve. --mock
# produces an offline placeholder so the pipeline is testable without a key.
ZAI_KEY=... ./scripts/lifestyle-shot.sh <name>                        # tier-2 lifestyle (default)
ZAI_KEY=... ./scripts/lifestyle-shot.sh --kind product-still <name>   # tier-1.5 product still

# Generate a tier-2 AI *motion clip* (cosmetic, geometrically approximate,
# and the motion itself is illustrative) from the prompt in
# designs/<name>/motion.conf via the Z.AI Vidu 2 image-to-video API (seeded
# from the design's committed tier-1 shot), transcode it to a GIF within the
# animation budget, and embed it with the disclosure readme-gate requires.
# Needs ZAI_KEY. CI runs it via the "Lifestyle clip (tier-2, AI motion)"
# workflow — automatically when a motion.conf lands on main, or on demand —
# and opens a draft PR to approve. --mock exercises the whole local pipeline
# (encode, budget, embed) without a key.
ZAI_KEY=... ./scripts/lifestyle-clip.sh <name>   # or: --mock

# Re-render a design's frozen preview shots from previews/cameras.conf
# (cameras are fixed across review rounds — see Design conventions)
./scripts/render.sh <name> --previews

# Labeled tolerance-sweep strip: N copies of the design's coupon (or entry
# part) across a parameter range, value embossed next to each copy
./scripts/render.sh <name> --sweep thread_tol=0.15:0.35:0.05

# Regenerate the README design gallery. CI regenerates and commits it; run it
# yourself to clear the "gallery is stale" failure from a local check.sh.
./scripts/gallery.sh

# Design-catalog category signal (issue #374): `check` validates every design's
# category against the closed vocabulary in designs/categories.conf; `order`
# emits the grouped, lineage-ordered sequence the gallery + site index consume.
./scripts/catalog.sh check
./scripts/catalog.sh order

# Build the static product site into build/site (--serve to preview it
# locally); this is the same command Vercel runs, so green here = deploy builds
./scripts/site.sh [--serve]

# Lift a design style out of a reference mesh into styles/<name>/ — the
# measured spec later designs build from and are checked against
./scripts/style-lift.sh <name> <reference.stl> --source <url> --license <terms>
./scripts/style-lift.sh --list

# Gate the style packs (tokens in sync, swatch renders and obeys its own
# rules) and every design that names a style in designs/<name>/style.conf
./scripts/style-check.sh [<style-or-design>...]

# Calling openscad directly means setting OPENSCADPATH yourself — the scripts
# above do it for you. Without it a `use <printability.scad>` / `use
# <threads-fdm.scad>` silently resolves to nothing: OpenSCAD only WARNs about
# the unknown modules, exits 0, and hands you a watertight sliceable STL with
# the features missing (the capsule comes out with a threadless neck). The
# trailing `:$PWD` is what resolves `include <styles/<name>/style.scad>`.
export OPENSCADPATH="$PWD/lib:$PWD"

# Render a design to STL manually (full CGAL render, catches geometry errors)
xvfb-run -a openscad -o build/<name>.stl designs/<name>/<name>.scad

# Render a single custom-angle PNG (rot is x,y,z camera rotation)
xvfb-run -a openscad -o build/<name>.png --imgsize=1200,900 \
  --camera=0,0,0,55,0,25,140 --viewall --autocenter designs/<name>/<name>.scad

# Override parameters without editing the file
xvfb-run -a openscad -o build/<name>.stl -D 'wall_thickness=2.4' designs/<name>/<name>.scad
```

`scripts/render.sh` produces `build/<name>.stl` plus `build/<name>.png`, a 2×2 contact sheet (iso / top / front / bottom-iso) — the bottom-iso view exists to check overhangs and bed contact, look at it. `scripts/check.sh` is the fast pre-commit check: it echo-checks every design and lib file (surfacing WARNINGs) and CGAL-renders the lib demo. `scripts/gate.sh --slice` is what CI actually enforces.

Workflow skills (`.claude/skills/`):

- **`/preflight`** — before any push: runs the exact checks CI runs (check.sh, gate.sh --slice, printcheck tests), scoped to what changed the same way CI scopes them, and answers "would CI pass?".
- **`/clear-prs`** — the **human-authorized backlog sweep**: takes every open PR to merged, closed-as-superseded, or open-with-a-named-blocker. Diagnoses all PRs in parallel (read-only: mergeable state, CI root causes from logs, review debt, conflict surface), triages the whole board before any fix (close/fix/merge, merge order, what protection actually requires), fans out one fixer worktree per disjoint PR (merge main in — never rebase; the derived-artifact conflict taxonomy; the semantic-trap hunt when `lib/` moved under a branch), then merges serially, re-verifying live state each time. Merging is the one act the autonomy routines never do — invoking this skill with an explicit "merge them" is that human decision, delegated in bulk and recorded in the final report.

## Repository layout

- `designs/<name>/<name>.scad` — one directory per design; the `.scad` file matching the directory name is the entry point. Notes, dimensions sketches, or variants live alongside it.
- `designs/<name>/README.md` — the design's **product page**, required and CI-gated (`scripts/readme-gate.sh`): what it is, preview images, print settings, and the parameters worth tuning — everything a stranger needs to decide to print it and succeed. `NOTES.md` stays the engineering log (decisions, derivations, session-resume context); don't duplicate it here. Start from `templates/README.md`.
- `designs/<name>/PM.md` — the design's **product charter**: customer, non-negotiables (with sources), what is explicitly out of scope, the ranked backlog, open decisions and a decision log, plus the **product-page art-direction brief** (the page promise, the tier-1 shot list, and any tier-2 lifestyle scenes) that `/art-direction` turns into shot manifests. This is what `/pm` enforces, and it is deliberately separate from NOTES.md (what happened) and README.md (what a stranger reads). Start from `templates/PM.md`; keep it under a page.
- `PM.md` (repo root) — the **platform's** product charter, one level up from the per-design ones (issue #272): what the *bench* is and who it is for, its non-negotiables (N1–N6, the standing decisions), the "never" list, the health invariants, and the platform backlog. This is what `/pm print-bench` enforces (Reeve, the operational PM) and what `people/reeve.md`'s mandate points at. Its opening paragraph is Reeve's mandate excerpt on the team page, so it leads with the platform-in-one-paragraph. Kept under a page like the design charters.
- `designs/<name>/animations.conf` — optional GIF-preview manifest (format documented in `scripts/animate.sh`). Each entry renders to a committed `previews/<anim>.gif` showing a key feature in motion — a turntable needs no model changes (camera spin); mechanism animations drive model motion from `$t` via an `anim` parameter (see sushi-battleship's shutter). The gate checks every entry has its GIF, embedded in the README, within the size budget. Compute `$t`-dependent values inside a geometry block, not in top-level assignments — top-level assignments evaluate before a `-D '$t=...'` override lands.
- `designs/<name>/shots.conf` — optional product-shot manifest (format documented in `scripts/product-shot.sh`). Each entry path-traces the exported STL into a committed `previews/<shot>.png` studio product shot for the README — the hero image a stranger sees first. The gate checks every entry has its PNG, embedded in the README, within the size budget. Shots are geometry-true (rendered from the same STL export the printable part uses), so they can never show a *feature* the print doesn't have — though shading still flatters, which is why the renderer smooths only finely-tessellated curves. Re-rendering an unchanged design reproduces the committed PNG pixel for pixel **on the same machine**; across machines expect near-identical but not byte-identical output (see `tools/photoshot/README.md`). CI is the canonical renderer for that reason — it regenerates a shot only for designs the PR actually moved, so cross-machine pixel wobble can never churn a design you didn't touch.
- `designs/<name>/product-still.conf` — optional tier-1.5 **AI product-still** manifest (format documented in `scripts/lifestyle-shot.sh`), one `<still> | seed=<ref> | <prompt>` per line. It sits between the geometry-true studio shot (tier 1) and the staged lifestyle scene (tier 2): the **bare part**, no scene, photoreal, from whatever angle sells its form — and, unlike the lifestyle shot, **shown on the page as a primary product image**. `scripts/lifestyle-shot.sh --kind product-still` (the same generator as the lifestyle shot, parameterized by `--kind`; **no new script**) runs the Z.AI GLM-Image API in **image-to-image** mode seeded from a committed tier-1 render (`seed=<ref>` → `previews/<ref>.png`) — but on this provider the seed does **not** constrain the shape to the real mesh (issue #302), so the still is AI and geometry-approximate, kept honest by its disclosure rather than any fidelity guarantee; an image-to-image still has no camera of its own, so a still's **angle _is_ the tier-1 shot it seeds** (a new angle means adding a `shots.conf` row, then a still that seeds it). It writes a committed `previews/product-still-<still>.png`, disclosed with the same `AI-styled scene` label and `geometry is approximate` caption `readme-gate.sh` requirement 9 enforces on every AI tier. The gate checks presence + disclosure, never pixels. Generation runs in CI (`.github/workflows/product-still.yml`, keyed on the `ZAI_KEY` secret): landing a `product-still.conf` on main fires it automatically — writing the manifest *is* the request — and it opens a draft PR to approve. Dispatch it by hand to re-roll a still. See `/product-shots` (tier 1.5).
- `designs/<name>/lifestyle.conf` — optional tier-2 **AI lifestyle-shot** manifest (format documented in `scripts/lifestyle-shot.sh`), one `<shot> | <prompt>` (or `<shot> | seed=<ref> | <prompt>`) per line. Unlike the geometry-true product shot, a lifestyle shot is **supplemental and cosmetic**: `scripts/lifestyle-shot.sh` runs the Z.AI GLM-Image API in **image-to-image** mode, seeded from a committed geometry-true render — a tier-1 studio shot or a tier-1.5 product still (`seed=product-still-<x>`) — (`seed=<ref>` → `previews/<ref>.png`, defaulting to the shot's own name); but on this provider the seed does **not** constrain the shape to the real mesh (issue #302), so the whole image is AI and geometry-approximate, kept honest by its disclosure rather than any fidelity guarantee, with the tier-1 render and STL remaining the source of truth for the real shape. It writes a committed `previews/lifestyle-<shot>.png`, disclosed with the `AI-styled scene` label and `geometry is approximate` caption `readme-gate.sh` requirement 9 enforces (the model still repaints, so the disclosure stays). It can't be regenerated deterministically, so the gate checks presence + disclosure, never pixels — the `.conf` drives the generator, not the gate. Generation runs in CI (`.github/workflows/lifestyle-shot.yml`, keyed on the `ZAI_KEY` secret): landing a `lifestyle.conf` on main fires it automatically — writing the manifest *is* the request — and it opens a draft PR to approve. Dispatch it by hand to re-roll a shot. See `/product-shots` (tier 2) and issue #66.
- `designs/<name>/motion.conf` — optional tier-2 **AI motion-clip** manifest (format documented in `scripts/lifestyle-clip.sh`), one `<shot> | <prompt>` (or `<shot> | seed=<ref> | <prompt>`) per line; `<shot>` should match an `animations.conf` or `shots.conf` entry so the clip sits beside the deterministic artifact it restyles. The motion sibling of `lifestyle.conf`, and doubly cosmetic: `scripts/lifestyle-clip.sh` animates the seeded shot — a committed tier-1 shot by default, or a lifestyle still via the explicit `seed=<ref>` field — with the Z.AI Vidu 2 image-to-video API — so the geometry is an impression *and the motion is illustrative* (the model can invent movement the print cannot perform; the `animations.conf` GIF stays the motion-true artifact) — transcodes the result to a committed `previews/lifestyle-<shot>.gif` within the animation-GIF budget, and embeds it with the same `AI-styled scene` label and `geometry is approximate` caption requirement 9 enforces on clips and stills alike. The gate checks presence + disclosure, never pixels. Generation runs in CI (`.github/workflows/lifestyle-clip.yml`, keyed on the `ZAI_KEY` secret): landing a `motion.conf` on main fires it automatically — writing the manifest *is* the request — and it opens a draft PR to approve. Dispatch it by hand to re-roll a clip. See `/product-shots` (tier 2) and issue #75.
- `designs/<name>/ARCHIVED` — presence marks a design **frozen at v0.1 and retired from active CI** (first line is the version, e.g. `v0.1`; the rest is a human note). An archived design is gated only by a **design-scoped** PR that edits its own files: every full-catalog run (the default-branch push, or any infra change under `lib/`, `scripts/`, or a CI workflow, where `gate_designs=ALL`) skips it across `gate.sh`, `regen`, `geo-diff` and `check.sh`, as does a scoped PR that reaches it only indirectly (blast radius, or a shared style) — so it never spends render, slice or product-shot cycles again. The one path that gates it is a scoped PR editing its own files, so the marker retires a design without stranding it. To revive one, keep the PR scoped to the design, or lift the `ARCHIVED` marker (which un-freezes it on every path, full-catalog runs included); the intended long-term route is to fork, update against current CI, and contribute the result back as a derivative. See "Archived designs (v0.1 freeze)" under Design conventions.
- `designs/<name>/team.conf` — the design's **core roster** (issue #123): `core:` names the member handles (`people/<handle>.md`) and `pm:` says which of them owns the product charter, in the house `key: value` conf format. Read by `site/lib/team.mjs`; a handle that doesn't resolve in the registry fails the site build. The shared review specialists are registry-wide (`shared: true`) and never appear in a core. Optional — a design without one is simply rosterless.
- `designs/categories.conf` — the **design-catalog vocabulary** (issue #374): the closed set of catalog groups (`nuggs`, the three `docs/advanced-techniques.md` technique domains, and `everyday-functional`) with their display labels, one `<slug> | <label>` per line (an optional third field, `<slug> | <label> | <blurb>`, is a promise line shown under a promise-bearing heading — `support-free` and `print-in-place` carry one telling a first-timer to leave slicer supports off; the three navigational headings don't). The line order is the **display order** of the groups in the README gallery and the site index. The single source of truth for the grouping both surfaces render; `scripts/catalog.sh` validates every design against it, emits the grouped order (`order`) and the group headings + blurbs (`groups`), so a new group, blurb or reorder is a one-file edit that regenerates the whole gallery (`ci-classify.sh` scopes it `regen_all`).
- `designs/<name>/catalog.conf` — the design's **catalog category** (issue #374): a single `category: <slug>` key in the house `key: value` conf format, the slug drawn from the closed vocabulary in `designs/categories.conf`. Every design that is **not a NUGGS module** carries one; a NUGGS module (named `nuggs`/`nuggs-*` **and** including `lib/nuggs-coupling.scad`) omits it because its group is derived from the name+coupling. The cross-check runs **both directions**: a design that includes the coupling but is not named `nuggs-*` fails, and a `nuggs-*`-named design that does **not** include the coupling is a name collision (e.g. `nuggs-yard`, named for the hamster, not the port) — not a NUGGS module, so it declares a `category:` like any other design. `scripts/catalog.sh check` (run by `check.sh`) refuses a free-text or typo'd category, a missing one, a NUGGS module that declares one, a coupling-including design not named `nuggs-*`, and a coupling-less `nuggs-*` name with no category. Editing it re-gates and re-renders that one design's gallery row.
- `designs/<name>/derives.conf` — lineage record of a **derivative design**, one that includes another design's entry `.scad` and redefines part of it (format and tooling: `tools/lineage`, background: `docs/derivative-designs.md`). Names the parent(s) in include order, the parent parts this design claims to replace, and any `diamond-ok:` assertions. Its presence turns on the derivative checks in `gate.sh`, which prove each claimed override actually changed the mesh — OpenSCAD reports nothing when a redefinition binds nothing, so the parent's part ships under the derivative's name, watertight and scoring 100/100.
- `lib/` — shared OpenSCAD modules. With `OPENSCADPATH` set, designs reference them as `use <printability.scad>` / `include <BOSL2/std.scad>`. Anything used by two or more designs belongs here. `lib/BOSL2/` (BSD-2-Clause) and `lib/NopSCADlib/` (GPL-3.0) are vendored third-party code — never edit either. The two licenses differ in reach: BOSL2's BSD-2-Clause is permissive, NopSCADlib's GPL-3.0 is copyleft and makes a design that includes it a combined work (see the license boundary in `LICENSE` and `lib/NopSCADlib/VENDORED.md`).
- `people/` — the **team registry** (issue #123): one `people/<handle>.md` per member, human or agent — a small `---`-fenced `key: value` header (name, kind, role, initials; `shared: true` for the repo-wide review specialists; a `mandate:` path for agents; an optional `github:` login that lets the team timeline attribute a git commit to the member — `site/lib/history.mjs`) with the body as a human's bio. An unresolvable handle, mandate path, or cited artifact fails `./scripts/site.sh`.

A design opts in with `include <printer-conf.scad>` (see `lib/printer-conf.scad`) to pre-fill its tuned-fit tolerances from the profile instead of a generic default; the "Log a print result" Action (`.github/workflows/log-print-result.yml`) can append measured deviations to a design's NOTES.md. Fully documented in `docs/print-feedback.md`.

## Design conventions

- Every design is parametric: user-tunable dimensions are declared as top-level variables at the top of the file with a comment giving units (always millimeters) and purpose. Use the OpenSCAD Customizer section syntax (`/* [Section] */`) so parameters are grouped.
- Declare `$fn` (or `$fa`/`$fs`) at the top of the file. Use a coarse value while iterating and note the production value in a comment; final STL renders should use smooth curves (`$fn >= 64` for visible cylinders, more for large-radius curves).
- Design for FDM printing unless the user says otherwise:
  - Default wall thickness ≥ 1.2 mm (3 perimeters at 0.4 mm nozzle).
  - Orient the model so it prints flat-side-down without supports where possible; chamfer (45°) rather than fillet the bottom edges of overhangs.
  - Holes for fasteners get 0.2–0.4 mm diameter clearance; press-fit and sliding fits get explicit tolerance parameters so the user can tune for their printer.
  - Avoid features thinner than 0.8 mm (2 extrusion widths).
- **Frozen preview cameras.** A design whose previews are reviewed across rounds keeps its shots in `designs/<name>/previews/`, driven by `previews/cameras.conf` (rendered via `./scripts/render.sh <name> --previews`; format documented in `scripts/render.sh`) with per-shot descriptions in `previews/CAMERAS.md`. Once a reviewer has seen a shot its camera is **frozen** — before/after comparisons across rounds must align — so a new region gets a new cameras.conf line; never move or reframe an existing one. The same policy applies to `animations.conf` and `motion.conf` entries.
- **Following a style.** A design that declares one in `designs/<name>/style.conf` must build from that style's tokens (`include <styles/<name>/style.scad>`) rather than retyping its numbers — then it satisfies the style's rules by construction, and `./scripts/style-check.sh` proves it on every printable part. A style is a constraint on *look*, not on printability: when the two conflict, printability wins and the exception gets recorded in NOTES.md.
- **Archived designs (v0.1 freeze).** A design that is done being iterated on — shipped, or deliberately retired without further work — is frozen at v0.1 by dropping a `designs/<name>/ARCHIVED` marker beside its entry `.scad`. The point is to stop spending CI cycles on a design nobody is going to change. The rule is one line: **an archived design is gated only by a design-scoped PR that edits its own files.** So it is skipped by every *full-catalog* run (a default-branch push, or any change under `lib/` or `scripts/` or to a CI workflow, all of which set `gate_designs=ALL`) — in `gate.sh`, in the `regen` and `geo-diff` jobs, and in `check.sh`'s syntax/link pass alike — and it is skipped even on a scoped PR when it was pulled in only *indirectly*: by a parent's blast radius, or by a shared style it declares (the `changes` classifier drops an archived design from the gated set unless the PR touched it directly). The one path that gates it is a scoped PR editing the design's own files, which is exactly what an in-place revival is. The full-catalog skip is deliberate and takes precedence: an archived-design edit *bundled into* a full-catalog run (a PR that also touches `lib/`, `scripts/`, or a CI workflow, forcing `gate_designs=ALL`) is still skipped, because the `ALL` path enumerates the tree with no record of what the PR touched. That is not a trap in practice — a real revival either keeps the PR scoped to the design, or lifts the `ARCHIVED` marker, which un-freezes it on *every* path including full-catalog runs. So archiving is reversible by working on the design again, and the intended way to evolve a frozen design is to fork the repo, bring it up to date against current CI, and contribute it back as a *derivative* (`docs/derivative-designs.md`) rather than editing the frozen original in place. The marker is presence-only; readme-gate, the gallery and the product site still include an archived design, so its page stays live — add a short archived banner under the README's H1 so a reader knows it is frozen.
- **Derivative designs.** A design that builds on another one — `include <../<parent>/<parent>.scad>`, then redefine the modules it wants different, so the parent's own call sites route to the redefinition — is a *derivative*, and ships `designs/<name>/derives.conf` recording its lineage (start from `templates/derives.conf`; the background, including the measurements, is `docs/derivative-designs.md`). Four rules follow from the fact that OpenSCAD reports **nothing** when a redefinition binds nothing:
  - The declared parent order must match the entry `.scad`'s include order. The last include silently wins on any name two parents share, so the order is the design, not bookkeeping.
  - `replaces:` is a claim the render gate settles, not a comment: it names the parent parts this design changes, and `gate.sh` proves each one by comparing exported meshes against the parent's. A part you meant to change and did not list is ungated; a part you listed and did not actually change is the typo'd-override bug, and fails.
  - A diamond (two parents sharing an ancestor) evaluates that ancestor twice and unions the duplicate cleanly, so nothing downstream can see it. It fails `lineage check` unless `diamond-ok:` names the ancestor, and that assertion is only true if the ancestor is **base-safe** — its top level defines modules and emits no geometry. The gate proves it by rendering the ancestor in every configuration it can ship in (its default render and each `ci.parts` value) and requiring zero facets from all of them: guarding top-level geometry behind a `part` value does not help, because the diamond doubles whatever that value draws. No design here qualifies today, and that is deliberate: base-safety only matters once a diamond actually exists, and the gate *refuses* an undeclared diamond rather than trusting it — so a design is made base-safe on demand, when the first diamond needs a base, never preemptively. When that day comes the recipe (which `gate.sh` prints too) is to make that ancestor's entry `.scad` a geometry-free module library — its top level defines modules and emits nothing in *every* config the gate renders it in, the default render and each `ci.parts` value — with the geometry that actually draws moved into the callers (the consuming derivative, or a separate part wrapper); verify by exporting each of those configs to an STL and running `./scripts/lineage.sh facet-count` on it (it takes the exported STL, not the `.scad`), each of which must count 0 — a geometry-free top level writes no STL at all and `facet-count` reports the absent file as 0, which is itself the proof. That is why converting is real work and not a rename: `gate.sh` and `render.sh` both render the same `designs/<name>/<name>.scad`, so an entry that emits nothing for the gate also has no default preview render, and the design's own previews and gallery row must first be moved onto explicit parts or `previews/cameras.conf` — the tension issue #52 weighed and deferred. Converting the reference `calibration-cube` for demonstration alone was considered and declined (issue #52): it would permanently split "the file you render" from "the file you read" in the one design newcomers open first, a real cost against a graph shape that has never occurred.
  - The derivative's `ci.parts` must cover its parents'. Part lists are per-design, so a derivative that ships none gates only its default render — and for a parent whose default is an unprintable assembled preview that is zero printable parts gated, green. `lineage check` requires the union; extra parts of your own are fine.
  - The product page documents the **delta** and links the parent's directory (`readme-gate.sh` requires the link). Everything the derivative did not change belongs on the parent's page, once.
- Designs may carry extra per-design docs beyond NOTES.md when a work phase needs its own brief — e.g. `sushi-battleship/HARDENING.md`, the review-round hardening work plan. They are preserved history, same as NOTES.md: keep them current or mark them closed, don't delete them.
- Designs with a tuned fit (threads, sliding doors, press-fits) ship a **"print this first" coupon**: `designs/<name>/<name>-coupon.scad`, a ≤10-line include-and-override wrapper on the production modules — never copied geometry — plus a "Print this first" section in NOTES.md saying what to tune and in what steps. The wrapper relies on OpenSCAD's include-then-override semantics: keep the overrides above any geometry statements. `gate.sh` picks the wrapper up automatically and gates `build/<name>-coupon.stl` (printcheck + test-slice) like any other part.
- **Print-feedback loop (opt-in, feature-flagged).** The digital gates prove printability in theory; the coupons exist because reality disagrees per printer. The loop (issue #101, full reference `docs/print-feedback.md`) captures that reality in three lightweight pieces, none of which anything else may hard-depend on: (1) `printer.conf` at the repo root — a printer's measured tolerances, `include <printer-conf.scad>` and read them (`printer_fit(nominal)` grows a dimension by the measured clearance); it ships **inert**, so opting in is safe and the off state is the default; (2) the **FIELD-TEST convention** — a `## Field test log` section in a design's NOTES.md recording each real print (`templates/FIELD-TEST.md`), kept last so entries append; (3) the **"Log a print result" Action** (`.github/workflows/log-print-result.yml`), a `workflow_dispatch` form that appends a FIELD-TEST entry and opens a draft PR, gated behind the single repo variable **`PRINT_FEEDBACK_ENABLED`** (unset/anything-but-`true` disables it with a `::notice::`). No new content-judging gate is added; `scripts/printer-conf-check.sh` and `field-test.sh --selftest` (both run by `check.sh`) prove the mechanism, presence-only.
- A design is not done until `render.sh <name>` succeeds (STL render completes without CGAL errors, PNG visually checked) **and** `gate.sh --slice <name>` exits 0 — printcheck watertightness/printability plus a PrusaSlicer test-slice. That is the bar CI enforces; `render.sh` alone is not it.

## Co-design workflow

This repo is used in a session-per-design pattern: the user starts a fresh session, brings one design idea, iterates on it here, and the finished design is committed back. Follow this loop:

1. **Brief.** Get the essentials before modeling: what the part does, the dimensions that matter (what it must fit/hold — ask for measurements), and anything printer-specific. Don't block on details you can default sensibly; state your assumptions. If the user cares how it *looks* — or shows you a model they like — settle the style here: pick one from `styles/` (`./scripts/style-lift.sh --list`), or lift a new one from their reference with `/style-spec` before modeling starts. Retrofitting a look onto a finished design means redoing the geometry.
2. **Scaffold.** Pick a kebab-case name, copy `templates/design.scad` to `designs/<name>/<name>.scad`, copy `templates/README.md` to `designs/<name>/README.md` (the product page — fill it in as the design takes shape; CI's readme-gate rejects designs without one), and create `designs/<name>/NOTES.md` recording: the goal, given measurements, key decisions, and intended print orientation. NOTES.md is what lets a later session resume the design cold — keep it current as decisions are made.
3. **Iterate preview-first.** After each meaningful change, run `./scripts/render.sh <name>` and send the user `build/<name>.png` (SendUserFile) so they react to the shape, not the code. Look at the bottom-iso view yourself for overhang/bed-contact problems before sending.
4. **Finish.** Complete the product page scaffolded in step 2. Give it a real product shot by writing a `shots.conf` and embedding the PNG the manifest declares (see `/product-shots`) — CI renders and commits the image itself, so the manifest and the embed are the parts you own. Same for `animations.conf` and `previews/cameras.conf`: declare the shot, let CI produce it. A design is done when the user approves the preview and `/preflight` comes back green — that skill defines the check set (it mirrors CI), so don't keep a competing list here. Send the final STL to the user as well — it's the deliverable they'll slice. **For a multi-part design whose parts print separately, the deliverable is the multi-object 3MF plate (`build/<name>-plate.3mf`, built by `plate.sh` from `ci.plate`), never the assembled render** — a single STL of two parts imports as one fused body and prints welded (the multi-part-fuse field test).
5. **Commit.** Commit the design directory (`.scad`, `README.md`, `NOTES.md`, any variants) with message `Add design: <name>` (or `Update design: <name>`). If a module written for this design is generally reusable, move it into `lib/` and mention it in the commit. Push to the branch designated for the session.

Multi-part designs (lids, hinged pairs, assemblies) stay in one design directory: either one `.scad` with a `part` parameter selecting what to render, or `<name>-<part>.scad` files next to the entry point — note the choice in NOTES.md. An **assembled render is a preview, never the sliceable deliverable**: STL carries no object separation, so a single STL of two parts imports as one fused body and prints welded (the multi-part-fuse field test). When the parts print **separately** (not print-in-place), ship a `designs/<name>/ci.plate` listing the production parts (a subset of `ci.parts`); `gate.sh` builds and gates `build/<name>-plate.3mf` — the parts as N distinct objects (`prusa-slicer --merge --export-3mf`, via `scripts/plate.sh`) — as the printable deliverable. The check is opt-in on `ci.plate` presence for now (`fusecheck`'s zero-blast-radius rollout — no existing design goes red); enforcing it for every separately-printed multi-part design, and migrating the existing traps, is the staged next step. Parts that print **together** as one file and must stay separable (print-in-place living hinges, captive sliders) are the different case `ci.fusecheck` / `fusecheck` covers, not `ci.plate`.

## Review skills

Reviewer personas live in `.claude/skills/` and can be invoked on any design PR or `designs/<name>/` directory. The pattern they follow — one persona = one lens + one reference pack + PM-gated tags, and the checklist for adding another — is documented in [docs/reviewer-personas.md](docs/reviewer-personas.md):

- **`/jane-review`** — real-world printability feedback as Jane, the person who will slice and print the part tonight: reviews this geometry against what stock slicer profiles actually do (feature sizes vs the nozzle, first-layer squish on the fits, seam defaults, bridge-angle auto-selection, bed exclusion zones) and QAs preview cameras before they freeze. Trusts CI's gates for the math — she consumes the posted printcheck/slice results instead of re-deriving or re-running them; her findings are tagged feedback the design's PM triages, not a merge gate.
- **`/drik-review`** — end-user/fitness-for-purpose feedback as Drik, the design's first real customer: walks a real session of use and re-ranks the backlog by usage frequency, checks payload fit and handling against what real-world objects measure, audits for information leaks (fog-of-war) that geometry checks can't catch, and polices product-page honesty. Trusts CI's gates for the math — never recomputes the designer's numbers; his findings are tagged feedback the design's PM triages, not a merge gate.
- **`/design-coach`** — becomes the dedicated review coach for one open design PR and drives evidence-first review rounds until it merges: CI's gates hold the numbers, Jane's and Drik's tagged findings flow through the PM's triage (`pm-triage` in `auto-review.yml`), and the coach turns triage verdicts into pushed iterations — resolving a thread only when the fix is visible in the diff, a committed preview, or CI's posted output, never by re-deriving anything.
- **`/oracle-review`** — the **cross-vendor, reasoning-blind Oracle** (issue #333, Foreman-baseline punch-list item #5): an independent frontier second opinion on every **autonomy PR** (`claude/*` head branches — design and tooling alike, unlike the design-only reviewers above), run by `.github/workflows/oracle.yml` on the vendor the shipper did **not** use — the workflow reads the ship routines' committed `provider:` keys and resolves the opposite role chain (`oracle-anthropic` / `oracle-glm`) from the #206 registry, defaulting to `oracle-anthropic` when the shipper is unknown (GLM-first shipping is the default, so Anthropic is the usual opposite). **Blind** means the reviewer sees only what trusted workflow bash assembles into `.oracle-context/` — the diff, the frozen `🚢 SHIP-LOCK` acceptance contract from the linked issue, and CI's posted results — never the shipper's session or chain-of-thought; it judges the artifact against the contract in both directions (no creep, no under-delivery, the same discipline as `/ship-issue`'s own scope audit) and posts exactly **one** tagged advisory comment via its `post_oracle_review` MCP tool (`.claude/skills/oracle-review/oracle_mcp.py` — a JSON-argument tool for the same `dontAsk`-matcher reason as the scout's, which hardcodes the marker, the advisory header and the attribution footer, pins the target PR to the workflow's `ORACLE_PR`, and caps posts at one per run). **Advisory, promotable**: its workflow is not in `ci-ok`'s `needs`, so a red Oracle never blocks a merge — promotion is a later branch-protection decision, the `security-scan.yml` posture. It ships its **own** gated deny backstop (`.claude/oracle-settings.json`, enforced by `scripts/oracle-perms-check.sh` — no wrapper exemption, since the Oracle has no shell wrapper) and runs with `--permission-mode dontAsk` over the read-only file tools plus that one MCP tool; the drift-guard tests (`tools/model-registry/tests/test_workflow_drift.py`) pin its ship steps to the registry chains, the single-vendor split of the two chains, and the backstop flag itself, each with a negative control. When the opposite-vendor chain is **exhausted** (every link failed), `oracle.yml` no longer bare-reds every PR (issue #347): it runs `model-registry classify <chain>` — a live 1-token probe that reduces the cause to `servable` / `dead` / `needs-human` / `transient` (the same taxonomy `model-smoke` uses, split so funding/auth separates from a retryable outage) — and branches on it, so a **human-fixable** provider failure (out of credit, or an invalid/missing key: `needs-human`) is raised **once** through the HITL `needs-decision` gate (a single deduped tracking issue keyed by a per-chain `<!-- oracle-provider-escalation:<chain> -->` marker, see `docs/decision-gate.md`) instead of reddening every autonomy PR, a genuinely unservable id (`dead`) still reds as the #298 registry defect it is, and a `transient` outage just retries next PR — the Oracle staying advisory throughout.
