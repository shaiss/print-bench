# The autonomy loop

The scheduled agent routines that keep the backlog moving without a human driving each step — what each one does, and the safety architecture that makes an unattended agent with a repo secret an acceptable thing to run. Work on this layer is platform work of the highest care tier: read this page *and* the linked design docs before touching it.

## The loop's shape

Issues are the loop's working substrate, routed by labels:

- **`/label-issues`** (the labeler) is the front door: it triages issues carrying no routing label and applies the one that routes each — chiefly `autonomy-ok` (single-PR-sized, non-design, unambiguous), or `declined-too-big`, `design-brief`, `needs-decision`. Add-only and conservative by construction.
- **The backlog burn** picks at most one `autonomy-ok` issue per firing — oldest first, skipping anything claimed or parked ([`tools/backlog-burn/README.md`](../../tools/backlog-burn/README.md) is the tested selection policy) — and runs `/ship-issue` on it, leaving a draft PR for human review.
- **`/ship-issue`** declines an oversized issue with `declined-too-big`; **the chunker** picks those up and files dependency-ordered sub-issues, auto-arming the genuinely small ones — so the burn always has shippable work and the human gate moves up to curating what is marked oversized.
- **The design run** is the same pattern pointed at `design-brief` issues: the whole co-design loop, converging on gates, never on taste — approving a *shape* stays the human's merge decision.
- **The product scout** originates: it reads committed signals (telemetry, field-test logs, the catalog) and files well-formed `design-brief` proposals. Advisory by construction — it never arms, approves, or merges.
- **The agent forge** ([docs/agent-forge.md](../agent-forge.md)) is the scout's tooling sibling with a judged second half: **Wright** (`/wright`) reads the bench's own pulse and files `agent-brief` proposals for new agents/tools; **Reeve's sign-off** (`/reeve-signoff`) rules on each — an approve arms it (`autonomy-ok` + `points-n`, so the burn builds it as a draft PR) behind a deterministic sensitive-path guard, a decline labels `wright-declined`, a needs-human parks it at the decision gate. The one routine whose write is escalation-shaped; shipped disarmed.
- **The groomer** and **Reeve** report: each upserts exactly one sticky report issue (backlog health; the platform's ops pulse) from deterministic detectors — no LLM in any finding.
- **The Oracle** posts one advisory cross-vendor review on every autonomy PR (`claude/*` head branches), run on the vendor the shipper did *not* use, blind to the shipper's session.
- **The decision gate** ([docs/decision-gate.md](../decision-gate.md)) is the loop's brake: `needs-decision` durably parks an issue out of every routine until a maintainer answers with `/decide yes|no <id>`; the label is the unspoofable verdict and a committed ledger is the audit trail.

## The safety architecture

Every routine sits inside the same defense stack. These are the invariants to preserve — and the checklist a reviewer will hold a new routine to (the build recipe is in [Extending the platform](extending.md)):

- **Two-key arming (the scheduled routines).** A scheduled routine acts only when its committed `.github/<routine>.conf` says `enabled: true` *and* its repo variable (`<ROUTINE>_ENABLED` — one per scheduled routine; the checked roster is the `ROUTINES` array in [`scripts/cadence-sync-check.sh`](../../scripts/cadence-sync-check.sh)) is `true`. The variable lives deliberately outside git: a fork can never inherit an armed agent, and flipping it off halts the routine in seconds. Some routines ship with the conf enabled and the variable unset — that is the intended disarmed state, not an inconsistency. The Oracle is the exception because it is event-driven, not scheduled: it fires on autonomy-PR events with no conf and no arming variable, and its off-switch is per-PR — the `no-oracle-review` label.
- **Graded write scopes.** Permissions follow what each routine actually writes: the burn and design run push branches and open PRs; the chunker, labeler, scout, assessor and the forge's two halves write issues only (Wright files `agent-brief`s; the sign-off comments verdicts and applies them from a closed label taxonomy); the groomer and Reeve write one sticky report issue; the Oracle posts one comment. Nothing gets `contents: write` it doesn't need.
- **Narrow surfaces.** The routines that read untrusted issue text while holding a provider key each get the narrowest surface that does their job, and the shapes differ by need — the labeler, scout, assessor and Oracle run `--permission-mode dontAsk` over an explicit allowlist; the chunker runs a narrow allowlist without it. Reads and simple writes go through a per-routine shell wrapper that enforces authorization itself (the labeler's wrapper refuses any issue outside the workflow-selected set; the chunker's files its sub-issues), while rich multi-line writes are per-routine MCP tools that hardcode their own guardrails — labels, markers, target pinning, per-run caps (the scout, assessor and Oracle). The ship routines that need the full toolchain run `bypassPermissions` instead — their boxing is the draft-PR human gate, not the tool surface. These postures are deliberate and not interchangeable; each workflow documents its own.
- **Deny backstops.** Because settings allows merge additively, each of the narrow-surface routines (chunker, labeler, scout, Oracle, assessor, and the forge's two halves) passes its own `.claude/*-settings.json` denying the inherited Bash allows and the sibling write surfaces its perms-check enumerates — guarded by a dedicated `scripts/<routine>-perms-check.sh` in `check.sh`, which also asserts the routine's *own* surface is never denied (or the scheduled run fails closed with no other signal). The forge's pair goes one further: each half's backstop denies the *other half's* MCP server (`scripts/wright-perms-check.sh` pins both directions), so the proposer can never judge and the judge can never file. The groomer and Reeve need none: they run no agent at all.
- **Default-branch pinning.** A secret-bearing scheduled workflow gates its job on the default branch *and* checks out the default branch with `persist-credentials: false` — a `workflow_dispatch` against a PR branch must never run unreviewed code with a secret. The Oracle goes further: it checks out the base branch and receives the PR strictly as data.
- **Liveness without livelock.** Ship runs post a `🚢 SHIP-LOCK` claim; [`scripts/routine-lock-cleanup.sh`](../../scripts/routine-lock-cleanup.sh) withdraws a dead run's lock (step timeouts sit below the job timeout precisely so the cleanup stays reachable) and escalates to `needs-decision` after repeated deaths; a final workflow step turns a dead run red so starvation can't disguise itself as health.
- **Models from the registry.** No workflow pins a model id: each consuming workflow resolves its chain — the stanza ids live in [`.github/models/registry.conf`](../../.github/models/registry.conf), which is the source of truth for chain names and contents alike (prose summaries elsewhere have drifted before — cite the file). The multi-link chains are walked link by link, first success winning; the deliberately single-link chains are consumed as exactly one link, so deepening them is a workflow change too, not just a registry edit. The four chain-walking routines (backlog-burn, design-run, chunker, labeler) walk their chain across providers since #544 — three GLM links, then an Anthropic tail (claude-sonnet-5 → claude-haiku-4-5) — as literal ship steps in file order, each gated on every earlier link not succeeding and on its own provider's key; the conf's `provider:` names the HEAD provider (link 1 must sit on it) and the resolve step's `model-registry shape --head <conf provider> --layout <the file's step order>` refuses a chain that does not fit slot for slot; the eight single-link routines keep every link on the conf's provider until #544 Part B; `model-smoke.yml` proves a chain's ids are actually servable, which no static check can.

## Operating it

Maintainer controls are GitHub-native and authorized by real repository permission: the arming variables, `/backlog-burn set <key> <value>`, `/decide`, `/ci-gate`, and each workflow's manual dispatch (with `dry_run` where it applies). The README's ["Operating the automation"](../../README.md) section is the operator summary; [docs/actions-security.md](../actions-security.md) records the accepted security posture around write-scoped dispatchable workflows; and the per-routine deep dives live in [tools/backlog-burn/](../../tools/backlog-burn/README.md), [tools/backlog-groomer/](../../tools/backlog-groomer/README.md), [tools/reeve/](../../tools/reeve/README.md), [tools/model-registry/](../../tools/model-registry/README.md) and the routine bullets in [CLAUDE.md](../../CLAUDE.md).
